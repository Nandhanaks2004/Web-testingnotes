SECTION 01

Pentesting Methodology

Professional penetration testing follows a structured, repeatable methodology. Each phase builds on the previous, creating a comprehensive security assessment.

01

Reconnaissance

Gather information about the target application, infrastructure, and attack surface.

02

Auth Analysis

Analyze authentication mechanisms, session management, and token handling.

03

Input Validation

Test input handling, output encoding, and injection vulnerabilities.

04

AuthZ Testing

Verify access controls, privilege boundaries, and object authorization.

05

Business Logic

Identify workflow flaws, trust assumptions, and logic vulnerabilities.

06

API Security

Assess API endpoints, method handling, and data exposure.

07

Session Security

Evaluate cookie security, session lifecycle, and invalidation.

08

Reporting

Document findings with evidence, impact, and remediation.

Key Principle

Never confirm a vulnerability without proper testing and evidence. Follow the cycle: Hypothesis → Testing → Observation → Analysis → Conclusion → Exploitation → Mitigation.

Assess input handling, reflection behavior, output encoding, URL parameter validation, and injection vulnerabilities across the application.

MEDIUM Reflected Input Without Output Encoding ▶

The newsletter subscription endpoint reflects user-supplied input directly inside JSON response messages without sanitization or encoding.

Risk

Although JavaScript execution was not observed in the current response context, this behavior indicates improper output encoding and unsafe reflection handling that may lead to XSS in future application changes.

MEDIUM Potential Stored XSS via Product Reviews ▶

The review submission feature accepts HTML/JavaScript payloads without sanitization. Payloads were stored and rendered inside the review section.

Attacker Consideration

LOW-MEDIUM Category Parameter Input Reflection ▶

SECTION 08

JWT Security Testing

JSON Web Tokens are not automatically secure. Investigate how authentication is implemented, whether validation is secure, and whether tokens can be modified.

🔐 Interactive JWT Anatomy Visualizer

Header { "alg": "HS256", "typ": "JWT" }
Payload { "username": "tester13", "exp": 1779706582 }
Signature HMACSHA256( base64UrlEncode(header) + "." + base64UrlEncode(payload), jwt_secret )
❌ Weak Secret
CRITICAL JWT Authentication Trust Bypass ▶

The application trusts client-controlled JWT claims. By modifying the username claim and re-signing with the weak secret, arbitrary authenticated sessions can be forged.

Token Forgery Flow
1. Extract JWT from cookie
2. Decode: { "username": "tester13", "exp": 1779706582 }
3. Modify: { "username": "admin", "exp": 1779706582 }
4. Re-sign using secret: "jwt_secret"
5. Replace Cookie: jwt=<FORGED_ADMIN_TOKEN>
6. Access: HTTP/2 302 Found → /dashboard

Critical JWT Security Principles

JWT ≠ automatically secure. Must validate properly. Client-side tokens are dangerous. Never trust claims blindly. Cookie flags matter for defense in depth. Asymmetric signing (RS256) prevents secret compromise.

SECTION 11

The Attacker Mindset

The difference between beginner testing and professional security research is not tools — it's mindset. Learn how to think like an attacker.

🚫

Beginner Mindset

❌ Try random payloads
❌ Look for instant results
❌ Follow click-by-click guides
❌ Expect vulnerabilities to be obvious

🧠

Professional Mindset

✓ Observe trust boundaries
✓ Question application behavior
✓ Form hypotheses, then test
✓ Analyze before exploiting

🧠 The Professional's Thought Process

1. Observe
What is the application doing? How does it handle data? What trust boundaries exist?
2. Hypothesize
"What if I modify this value?" "Does the server validate this?" "Can I bypass this check?"
3. Test
Make one controlled modification. Observe the response. Compare with expected behavior.
4. Validate
Verify the finding is real. Eliminate false positives. Document evidence.

Key Principle

A normal user sees functionality. An attacker sees trust boundaries. Every input field, every API call, every cookie — ask yourself: "What happens if I change this?"

SECTION 12

Lessons Learned

Understanding why vulnerabilities happen is more important than knowing how to exploit them. Here are the core lessons from this assessment.

❓

Why Vulnerabilities Happen

Developers trust client input, assume valid data, and overlook business logic. Security is often an afterthought in development cycles.

🛡

Backend Validation Matters

Frontend validation is for convenience. Backend validation is for security. Never trust client-controlled data.

🔗

APIs Increase Attack Surface

Every API endpoint is a potential entry point. Hidden endpoints, mass assignment, and missing authorization are common API flaws.

🔐

JWT Is Not Automatically Secure

Weak secrets, algorithm confusion, and trusting client claims turn JWT into a critical vulnerability rather than a security control.

📊

Business Logic Flaws

Security is not only XSS and SQLi. Workflow abuse, quantity manipulation, and trust model failures cause real-world breaches.

👤

Authorization Is Difficult

Object-level authorization requires checking ownership/permissions at every resource access. Missing checks lead to IDOR and data leaks.

❌ Insecure Code Example

if (quantity >= 0) {
  addToCart(productId, quantity);
}

Accepts zero, negative, and unlimited values

✅ Secure Code Example

if (quantity > 0 && quantity <= 100) {
  addToCart(productId, quantity);
} else {
  reject("Invalid quantity");
}

Validates range, rejects invalid input server-side

SECTION 14

Student Exercises

Test your understanding. Each exercise requires investigation, observation, and analysis — not just payload repetition.

EXERCISE 01

Authentication Flow Analysis

You intercept a login request to POST /login. The server returns a 302 redirect and sets a JWT cookie. What security checks should you perform on this cookie?

Check: Secure flag, HttpOnly flag, SameSite attribute, token expiration, algorithm used, secret strength.
EXERCISE 02

JWT Trust Model

You decode a JWT and find the payload contains {"username":"tester13","role":"user","exp":1779706582}. You modify "role" to "admin" and re-sign with a guessed secret. The server accepts the token. What vulnerability does this confirm?

This confirms JWT authentication trust bypass. The server trusts client-controlled claims without proper validation.
EXERCISE 03

Business Logic Discovery

You send quantity=0 to POST /add-to-cart/<id> and the product is added with quantity 0 and price ₹0.00. What are three possible exploitation scenarios?

Free purchase (checkout with zero total), negative quantity abuse (refund manipulation), integer overflow (crash/stock corruption).
EXERCISE 04

CSRF Attack Vector

The application uses cookie-based authentication with SameSite=Lax. Sensitive POST endpoints lack CSRF tokens. How would you construct a proof-of-concept for a checkout CSRF?

Create an HTML form that auto-submits POST to /checkout. When a victim opens the page, the browser automatically sends their session cookie.
EXERCISE 05

Reflection vs Execution

You send {{7*7}} to GET /category/{{7*7}}. The response shows "Products in {{7*7}}" (not "Products in 49"). What does this prove, and what does it NOT prove?

It proves reflection exists. It does NOT prove SSTI execution. Professional testers differentiate between reflection and template evaluation.
EXERCISE 06

IDOR Investigation

You notice POST /remove_from_cart/686f6dd89bee9e8d8b3416c7 uses a direct object reference. What additional tests should you perform to confirm an IDOR vulnerability?

Test with another user's session, try other user's cart IDs, check if cart ownership is validated server-side, test with unauthenticated requests.
